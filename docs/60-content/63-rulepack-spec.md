# 63 — Rule pack authoring format

> **Status:** Proposed

Companion document: `docs/10-core/12-rule-engine.md` (the engine). That document specifies
the machine and the evaluation model. This one specifies the document format an author
writes, field by field, with defaults and validation.

Owner brief §5.2 gives the seed. Everything here extends it; nothing here contradicts it
except one citation, which is called out as a proposed change in §16.

The reader this is written for: a network engineer who can explain why
`perfect-forward-secrecy` on one side and absent on the other fails Phase 2 while Phase 1
stays up, and who has never written a parser. If a field in this spec requires programming
knowledge to fill in correctly, that field is wrong.

## 1. What a rule is

One declarative document defining one finding. Not a check script, not a template, not a
policy. It answers six questions and the format forces all six:

| Question | Field |
|---|---|
| What is wrong? | `title`, `condition` |
| What is it wrong *about*? | `applies_to` |
| Why does it matter? | `why` |
| What does it look like when it bites? | `symptom_if_mismatched` |
| What do I do about it? | `remediation`, `verify`, `rollback` |
| When is it fine to leave? | `acceptable_when` (mandatory, invariant 8) |

A rule that cannot answer all six is not ready. The format makes that a build failure
rather than a judgement call.

### 1.1 Normative validator

The normative schema is a JSON Schema generated from the Rust types (`schemars`) and
published with each engine release as `schemas/rule-<engine-version>.json`. This document is
the human-readable specification; where the two disagree, the generated schema is a bug in
one of them and both get fixed. Editors validate against the published schema; CI validates
against the engine binary, which is the same code path the app uses.

## 2. Pack layout on disk

```
fathom.ipsec/
├── pack.toml                       # manifest (§3)
├── LICENSE
├── CHANGELOG.md                    # required; see §3.4
├── rules/
│   ├── ipsec.pfs.absent/
│   │   ├── rule.yaml
│   │   └── fixtures/
│   │       ├── fire-cbc-no-pfs.yaml
│   │       ├── fire-parsed-absent.yaml
│   │       ├── pass-group14.yaml
│   │       └── pass-ikev2-first-child.yaml
│   ├── zone.host-inbound.ike-missing/
│   │   └── …
│   └── …
├── explainers/                     # long-form Teaching text too big for rule.yaml
│   └── explain-rule-ipsec.pfs.absent.md
├── i18n/
│   ├── en.yaml                     # generated by extraction; checked in
│   ├── de.yaml
│   └── ja.yaml
├── golden/
│   ├── junos-srx-clean.set         # must produce zero findings (engine §15.3 gate 3)
│   └── panos-clean.xml
└── snapshots/
    └── srx-branch-01.snapshot.yaml # engine §15.4
```

Rules:

| Rule | Reason |
|---|---|
| One directory per rule, named exactly the rule id | `git log rules/ipsec.pfs.absent/` is the history of one finding. |
| `rule.yaml` is one document, no multi-doc YAML | A file is a rule. Diffs stay legible. |
| Fixtures live with the rule, never in a central `tests/` | A rule and its evidence move together, including when it is withdrawn. |
| Explainer bodies may be Markdown files referenced by key | `teaching` text runs to several hundred words and YAML block scalars stop being reviewable at that length. |
| `i18n/en.yaml` is generated, not hand-edited | §14. |

## 3. `pack.toml`

```toml
[pack]
id            = "fathom.ipsec"
name          = "Fathom IPsec baseline"
version       = "2.4.1"
description   = "Site-to-site IPsec findings for Junos SRX, PAN-OS and IOS-XE."
license       = "CC-BY-SA-4.0"
homepage      = ""                                  # may be empty; never fetched (invariant 1)
expires       = "2027-09-01"                        # §13.7 of the engine doc

[compat]
schema_range  = "vers:fathom/>=3.0.0|<4.0.0"
min_engine    = "1.2.0"
max_engine    = "2.0.0"

[content]
rule_count    = 148
tree_hash     = "blake3:9f2c…"                      # over the canonicalised rules/ tree
locales       = ["en", "de", "ja"]

[[maintainers]]
name  = "…"
role  = "reviewer"                                  # reviewer | author | owner
```

| Field | Type | Required | Default | Validation |
|---|---|---|---|---|
| `pack.id` | string | yes | — | `^[a-z0-9]+(\.[a-z0-9-]+)+$`, reverse-DNS, ≤ 64 chars. Must match the signing key's scope (engine §13.3). |
| `pack.name` | string | yes | — | ≤ 80 chars, no vendor trademarks implying endorsement. |
| `pack.version` | semver | yes | — | Bump policy in engine §13.4. |
| `pack.license` | SPDX id | yes | — | Must be an SPDX identifier. |
| `pack.homepage` | string | no | `""` | Recorded and displayed. **Never fetched.** Invariant 1. |
| `pack.expires` | date | no | build date + 400 days | Past it, findings are labelled stale. Never auto-disabled. |
| `compat.schema_range` | `vers:` range | yes | — | §6.1. Upper bound should be generous; the schema is additive-only within a major (engine §14.2). |
| `compat.min_engine` / `max_engine` | semver | yes | — | The `fex` language + builtin table version, not the app version. |
| `content.rule_count` | int | yes | — | Must equal the count of `status: active` + `deprecated` rules. A mismatch is a build error, which catches a rule file that failed to be added to git. |
| `content.tree_hash` | `blake3:<hex>` | yes | — | Over the canonicalised tree. Recomputed and compared on install. |
| `content.locales` | list | yes | `["en"]` | `en` must be present. |
| `maintainers` | table array | yes, ≥1 with `role = "reviewer"` | — | Invariant 10: a named human reviewer. |

### 3.4 `CHANGELOG.md`

Required, and required to name every rule id whose severity or condition changed, because
that is what a downstream consumer needs to diff their CI gate against. Format is free; the
gate is only that every `major` and `minor` version has an entry and that entry mentions at
least one rule id.

## 4. The rule document — complete field reference

The full surface. `R` = required, `O` = optional.

### 4.1 Identity and lifecycle

| Field | Type | R/O | Default | Validation |
|---|---|---|---|---|
| `id` | string | R | — | Dotted, lowercase, `^[a-z][a-z0-9]*(\.[a-z0-9-]+)+$`, 2–5 segments. **Stable forever** (conventions). First segment is the domain (`ipsec`, `ike`, `zone`, `mtu`, `route`, `nat`, `ha`, `mgmt`). Must equal the containing directory name. |
| `rule_version` | semver | R | — | Bumped when the rule's own content changes; lets a finding in an old export be traced to the exact text that produced it. |
| `status` | enum | O | `active` | `draft` \| `active` \| `deprecated` \| `withdrawn`. `draft` compiles and is fixture-gated but never fires in a release build. `withdrawn` never fires anywhere; the id is retained forever. |
| `replaced_by` | rule id | O | — | Required when `status` is `deprecated` or `withdrawn`. May reference another pack. |
| `reviewed_by` | string | R | — | A named human. Invariant 10. Not an email — a name a colleague recognises. |
| `reviewed_on` | date | R | — | ISO date. Lint warns when older than 24 months. |

### 4.2 Classification

| Field | Type | R/O | Default | Validation |
|---|---|---|---|---|
| `severity` | enum | R | — | `info` \| `low` \| `medium` \| `high`. Engine §9.2. Pack-wide budget: ≤15% `high`. |
| `confidence` | enum | O | `definite` | `definite` \| `probable` \| `heuristic`. Engine §9.3. |
| `category` | enum | R | — | `correctness` \| `security` \| `interop` \| `operability` \| `hygiene`. |
| `tags` | list of string | O | `[]` | Free-form, lowercase, hyphenated. Used for filtering only, never for logic. `[phase1, phase2, mtu, nat, ha, day-one, bring-up]`. |

**`category` guidance** — the distinction that matters most in review:

| Category | Fires when | Field card example |
|---|---|---|
| `correctness` | It will not work. | Missing `host-inbound-traffic system-services ike` |
| `security` | It works, and it is weaker than the owner would accept. | PFS absent; `dh-group group2` |
| `interop` | It works with this peer and will not with the next one. | No `traffic-selector`, so the SRX proposes `0.0.0.0/0` |
| `operability` | It works, and you will not be able to diagnose or fail it over. | `establish-tunnels on-traffic` on a monitored backup; no `vpn-monitor` |
| `hygiene` | It works, and it will cost someone time later. | `traceoptions` left enabled; `proposal-set standard` |

### 4.3 Applicability

| Field | Type | R/O | Default | Validation |
|---|---|---|---|---|
| `platforms` | list of platform id or glob | R | — | §5. Non-empty. Every entry resolves in the platform registry. |
| `platforms_exclude` | list of platform id | O | `[]` | Applied after `platforms`. |
| `versions` | string or map | R | — | §6. `"*"` is legal and means all versions of all listed platforms. |
| `on_unknown_version` | enum | O | `unprovable` | `unprovable` \| `skip` \| `fire`. Ignored when `versions` is `"*"` (which always fires). |
| `applies_to` | object | R | — | §7. |
| `requires` | list of evidence class | O | `[]` | `peer_config` \| `runtime_output` \| `path_mtu` \| `software_version` \| `transit_config`. Engine §8.2. |
| `on_unset` | enum | O | `pending` | `pending` \| `skip` \| `fire`. Engine §2.2. Lint warns if >10% of a pack uses `fire`. |

### 4.4 Logic

| Field | Type | R/O | Default | Validation |
|---|---|---|---|---|
| `condition` | `fex` expression | R | — | Must type-check to `bool`. Read-set must extract (engine §5.3). ≤2,000 VM steps on every fixture. |
| `discriminator` | `fex` expression | O | — | Must type-check to `str`. Required when the rule can fire more than once per anchor; a second firing without one is a fixture-suite failure. |

### 4.5 Prose (all localisable, §14)

| Field | Type | R/O | Default | Validation |
|---|---|---|---|---|
| `title` | string | R | — | ≤ 72 chars, no trailing period, states the *state*, not the action. "Perfect Forward Secrecy is not configured", not "Configure PFS". |
| `why` | text | R | — | 20–600 chars. Must state a consequence, not a definition. Banned-phrase gate applies. |
| `symptom_if_mismatched` | text | O | — | Required when `category` is `interop` or `correctness`. What it looks like when it bites — the misdiagnosis it prevents. |
| `explain.terse` | string | R | — | ≤ 80 chars, one line, no markup. §11. |
| `explain.explained` | text | R | — | 1–3 sentences, 80–400 chars. Inline `code` allowed. §11. |
| `explain.teaching` | text or `file:` ref | R | — | ≥ 200 chars. Must contain ≥1 named failure mode and ≥1 counterfactual. §11. |
| `acceptable_when` | text | **R** | — | Invariant 8. Never empty. If never acceptable, say so explicitly (§10). |

### 4.6 Action

| Field | Type | R/O | Default | Validation |
|---|---|---|---|---|
| `remediation` | object | O | — | §9. Either `patch` or per-platform `lines`. A rule with no remediation must set `remediation_absent_reason`. |
| `remediation_absent_reason` | string | conditional | — | Required when `remediation` is absent. Forces the author to say why there is no fix ("this is a peer-side change"). |
| `rollback` | object | conditional | — | **Required** when any remediation line's `risk` is `Disruptive`. |
| `verify` | list of command corpus id | O | `[]` | Every id must resolve. Rendered as the "prove it worked" ladder. |

### 4.7 Relations

| Field | Type | R/O | Default | Validation |
|---|---|---|---|---|
| `supersedes` | list of rule id | O | `[]` | Engine §12.1. DAG, depth ≤3. |
| `requires_finding` | list of rule id | O | `[]` | Engine §12.3. Same DAG. Each entry needs a `why_chained` line. |
| `why_chained` | map rule id → string | conditional | — | Required when `requires_finding` is non-empty. |
| `next_if_bad` | list of ref | O | `[]` | §13. `{command: …}` or `{rule: …}`. Navigation only, no evaluation effect. |
| `related` | list of ref | O | `[]` | §13. |

### 4.8 Provenance of the rule itself

| Field | Type | R/O | Default | Validation |
|---|---|---|---|---|
| `sources` | list of citation | R | — | §12. May be `[]` only with `sources_note`. |
| `sources_note` | string | conditional | — | Required when `sources` is empty. |

## 5. Platform predicates

### 5.1 The registry

Platform ids are **not** free text. They come from a registry in the graph schema
(`schema/platforms.yaml`), not from packs, so that a rule id means the same thing to
everyone.

```yaml
# schema/platforms.yaml  (excerpt — the registry is schema, not pack content)
junos-srx:   { vendor: juniper,  family: junos, version_scheme: junos }
junos-mx:    { vendor: juniper,  family: junos, version_scheme: junos }
junos-ex:    { vendor: juniper,  family: junos, version_scheme: junos }
panos:       { vendor: palo-alto, family: panos, version_scheme: panos }
ios-xe:      { vendor: cisco,    family: ios,   version_scheme: iosxe }
nx-os:       { vendor: cisco,    family: nxos,  version_scheme: nxos }
eos:         { vendor: arista,   family: eos,   version_scheme: eos }
fortios:     { vendor: fortinet, family: fortios, version_scheme: fortios }
```

Terminology: a **platform** is vendor+family (conventions). `junos-srx` and `junos-mx` are
two platforms of one vendor, and IPsec rules that are true on one are frequently false on
the other — SRX is flow-based, MX is packet-based with a services PIC, and the
configuration hierarchy differs. Writing `platforms: [junos-*]` on an SRX rule is the most
common authoring mistake in this whole format.

### 5.2 Syntax

```yaml
platforms: [junos-srx]                       # exact, preferred
platforms: [junos-srx, panos, ios-xe]        # explicit list
platforms: ["junos-*"]                       # single-level glob, whole family
platforms: ["*"]                             # every platform — needs justification (§5.4)
platforms_exclude: [junos-ex]                # applied after
```

| Form | Allowed | Note |
|---|---|---|
| Exact id | yes | Always preferred. |
| `<family>-*` | yes | One level only. `junos-*` matches `junos-srx`, `junos-mx`, `junos-ex`. |
| `*` | yes, with lint warning | Requires a `# platform-wildcard: <reason>` comment on the line. |
| Nested glob (`ju*-s*`) | **no** | Build error. Globs that need thinking about are globs that select the wrong thing. |

### 5.3 Enums across platforms

A rule targeting three platforms must not compare an enum field to a vendor spelling. The
schema declares neutral variants and a per-platform map:

```yaml
# schema/enums/establish_tunnels.yaml
variants: [immediately, on_traffic, responder_only, responder_only_no_rekey]
default_by_platform:
  junos-srx: on_traffic
platform_spellings:
  junos-srx:
    immediately:    "immediately"
    on_traffic:     "on-traffic"
    responder_only: "responder-only"
```

Rules write `enum_is(establish_tunnels, "on_traffic")`. Comparing an enum field to a string
literal with `==` is a build error (engine §3.7). The emitter, not the rule, produces the
vendor spelling.

`default_by_platform` is what makes `FieldState::Default` computable, which is what makes
`is_default()` meaningful, which is what lets a rule distinguish "they wrote the default
down" from "they inherited it".

### 5.4 When one rule should be several

**RECOMMENDATION — split a rule per platform the moment `remediation` needs a `when:` on
any hole, or `why` needs a "on PAN-OS, however" clause.** One rule id per behaviour, not one
per idea. The engine cost of two rules is negligible; the review cost of a rule whose text
is true on one platform and misleading on another is not.

## 6. Version predicates, and Junos

Owner brief §5.2: *"Version predicates are not optional. Junos syntax differs meaningfully
between 15.x, 21.x and 23.x. A rule that is correct on one and wrong on another is worse
than no rule."*

### 6.1 Syntax: `vers`

Fathom adopts **VERS**, the version-range specifier from the Package-URL project
(`package-url/vers-spec`), rather than inventing one.

```
vers:<versioning-scheme>/<constraint>|<constraint>|…
```

Constraints are `<comparator><version>` with comparators `=`, `!=`, `<`, `<=`, `>`, `>=`,
or a bare version meaning `=`. Alternatives are `|`-separated. Constraint pairs form
intervals.

```yaml
versions: "*"                                        # everything, always fires
versions: "vers:junos/>=15.1R1"                      # open upper bound
versions: "vers:junos/>=15.1R1|<23.4R1"              # half-open interval
versions: "vers:junos/>=15.1X49-D100|<15.1X49-D240"  # within one X train
```

Per-platform map form, for a rule whose applicability differs by platform:

```yaml
versions:
  junos-srx: "vers:junos/>=15.1R1"
  panos:     "*"
  ios-xe:    "vers:iosxe/>=16.12.0"
```

Every platform in `platforms` must have an entry in the map form, or the build fails.
Silence about a platform you claimed to cover is the failure mode this catches.

### 6.2 Fathom-local versioning schemes

VERS defers the comparison semantics to the scheme. The schemes below are **Fathom's
definitions**, not the vendors'. They are declared here so a rule author can predict what a
range does, and they live in `schema/version-schemes/` so the engine and the linter share
one implementation.

#### `vers:junos/`

Junos release numbering is `m.nZb.s` — main release, minor release, release type, build,
spin — with service releases appended. Real examples: `23.4R1.9`, `21.4R3-S5.4`, `20.4R3-S9`,
`15.1X49-D240`. The `X` releases are a separate numbering scheme for special releases, and
the SRX branch line lived there for years.

**Grammar:**

```
junos      ::= major "." minor train [ "-" service ] [ "." spin ]
train      ::= "R" build
             | "X" xnum "-D" dnum
service    ::= "S" snum
major, minor, build, xnum, dnum, snum, spin ::= digits
```

**Comparison — the awkward part, and the honest answer.**

Comparing `15.1X49-D240` with `15.1R7` is not a well-formed question. They are different
trains with different content, and neither is "after" the other in any way a rule should
depend on. Ordering them by string, or by pretending `X49` is a build number, produces a
rule that is confidently wrong on a platform the author never had.

| Case | Result |
|---|---|
| Different `major.minor` | Compare `(major, minor)` numerically. `15.1X49-D240 < 21.4R3` — **comparable.** |
| Same `major.minor`, same train identity | Compare `(build, service, spin)` or `(dnum, spin)` numerically, missing components as 0. `21.4R3-S5.4 > 21.4R3-S5` — **comparable.** |
| Same `major.minor`, different train identity | **Incomparable.** `15.1X49-D240` vs `15.1R7` returns `Incomparable`. |

Train identity is `"R"` for standard releases and `("X", xnum)` for exception trains, so
`15.1X49-D100` and `15.1X49-D240` are comparable but `15.1X49-D240` and `15.1X53-D50` are
not.

<!-- VERIFY: that no Junos train has shipped a release where major.minor ordering
contradicts chronological ordering across trains. The rule above assumes major.minor is a
reliable coarse ordering even between R and X trains; that matches every release pair I can
name but has not been checked exhaustively against Juniper's release matrix. -->

**What `Incomparable` does.** A bounded `versions` predicate that needs an incomparable
comparison evaluates to `Incomparable`, and the engine produces
`Unprovable(VersionIncomparable)` — an entry in the "could not evaluate" band naming the
recorded version, not a finding and not silence (engine §8.3). The fix is for the author to
name the train:

```yaml
versions:
  junos-srx: "vers:junos/>=15.1X49-D100|<15.1X49-D240|>=17.3R1"
```

#### `vers:panos/`

```
panos ::= major "." minor "." maintenance [ "-h" hotfix ]
```
Examples: `10.2.9`, `11.1.4-h7`. Order `(major, minor, maintenance, hotfix)`, hotfix absent
= 0.

<!-- VERIFY: that PAN-OS hotfixes within one maintenance release are cumulative and
strictly ordered, i.e. that -h7 contains everything in -h1..-h6. If they are not cumulative,
`>=11.1.4-h3` is a misleading predicate and the scheme needs to treat hotfix as a set
rather than an ordinal. -->

#### `vers:iosxe/`

```
iosxe ::= major "." minor [ "." rebuild ] [ letter ]
```
Examples: `16.12.5`, `17.09.04a`. Minor is compared numerically, so `17.09` and `17.9` are
equal (leading zeros are stripped). A trailing letter orders **after** the same version with
no letter: `17.09.04 < 17.09.04a < 17.09.04b`.

<!-- VERIFY: the letter-suffix ordering for IOS-XE rebuilds, and whether a lettered rebuild
is always a superset of the unlettered one. -->

### 6.3 `on_unknown_version`

The graph may not record a version — the user typed a config in by hand, or pasted a
fragment.

| Value | Behaviour | Use for |
|---|---|---|
| `unprovable` (default) | `Unprovable(VersionUnknown)`. Counted in the "could not evaluate" band. | Any rule whose truth actually depends on the version. |
| `skip` | Silent. | Rules where the version predicate is a narrowing optimisation, not a correctness condition. Rare; lint asks for a comment. |
| `fire` | Evaluate as if in range. | Rules where being wrong on an out-of-range version is cheaper than missing it everywhere. Requires a comment. |

`versions: "*"` always fires and ignores this field.

**RECOMMENDATION — set the version on a device the moment you know it.** The findings panel
should offer "3 checks need a software version → [set version]" as a one-field action
(engine §8.4). Version is the cheapest evidence in the product and it unlocks the most
rules.

## 7. `applies_to` — the selector

Full reference in engine §4. The authoring surface:

```yaml
applies_to:
  kind: LogicalUnit                     # required, exactly one — the anchor kind
  where: "matches(name, /^st0\\.[0-9]+$/)"   # optional; anchor fields only
  canonical: peer                       # optional; symmetric rules fire once (engine §4.5)
  with:
    zone:
      via: zone_binding                 # an edge ROLE from the schema
      card: optional                    # one | optional | many   (default: one)
      reverse: false                    # default false
    device:
      via: [parent_interface, parent_device]   # chain, ≤3 hops
      card: one
```

| Field | R/O | Default | Validation |
|---|---|---|---|
| `kind` | R | — | Must exist in the schema. Findings attach here. |
| `where` | O | — | `fex` → `bool`. Anchor fields only; **no bindings in scope**. ≤50 VM steps (engine §15.3 gate 7) because it runs over the whole kind population. |
| `canonical` | O | — | Names a binding with `card: one`. The instance evaluates only when `anchor.id < binding.id` by ULID order. |
| `with.<name>.via` | R | — | One edge role, or a list of ≤3. Roles, never field paths or names (invariant 7). |
| `with.<name>.card` | O | `one` | `one` \| `optional` \| `many`. `one` failing is a graph integrity error, not a finding. |
| `with.<name>.reverse` | O | `false` | Requires the schema to declare the role reverse-indexed. |

Binding names are identifiers visible in `condition`, `discriminator` and remediation
templates. `self` is reserved and refers to the anchor; anchor fields are also readable
bare.

**Lint limits:** ≤6 bindings, ≤3 hops per binding, and the static read-set may not exceed
2× the largest observed dynamic read-set across fixtures. Binding six neighbours to read one
is a rule that will be woken six times too often for the rest of its life.

## 8. `condition` — authoring guidance

The language is `fex` (engine §3). Its full grammar, value lattice and builtin table are
there. What belongs here is the authoring advice, because the language is small enough that
the mistakes are predictable.

### 8.1 Say what you mean about absence

Four field states (engine §2), and the right predicate depends on which fact you have:

| You mean | Write | Not |
|---|---|---|
| "The parsed config proves this statement is not there." | `known_absent(pfs_group)` | `pfs_group == null` |
| "Nobody has decided this yet, in a config or by hand." | `!has(pfs_group)` with `on_unset: pending` | `pfs_group == null` |
| "The value is present and is X." | `pfs_group == 14` | `has(pfs_group) && pfs_group == 14` |
| "They wrote the default down explicitly." | `is_default(dpd_interval)` | `dpd_interval == 10` |

`pfs_group == null` is legal and reads `null` for both `Unset` and `Absent`. It is the right
choice only when the rule genuinely does not care which. In a linter that runs while you
type, it usually does care.

### 8.2 Do not encode a vendor spelling

```yaml
# wrong — true on Junos, meaningless on PAN-OS, and this rule claims both
condition: "establish_tunnels == 'on-traffic'"

# right
condition: "enum_is(establish_tunnels, 'on_traffic')"
```

### 8.3 Prefer a positive fact to a double negative

`!peer_ts.exists(t, mirrors(self, t))` is fine. `!(!has(x) || y)` will be read wrong in
review. The checker will not stop you; the reviewer should.

### 8.4 Keep `where` cheap

`where` runs over every node of the anchor kind. Regex is charged per input byte. A
`where` that calls `matches` on a long field over a 20,000-node kind is the one authoring
mistake that shows up as UI jank rather than as a wrong finding. Filter on an enum or an
integer when you can and leave the regex to the condition.

### 8.5 One rule, one fact

If `condition` has a top-level `||` between two unrelated facts, it is two rules. They will
want different severities, different remediations and different `acceptable_when` text
within six months, and splitting them later means changing rule ids, which is forbidden.

## 9. `remediation` — templating

### 9.1 Two forms, and the preferred one

Invariant 6: emitters return `(line, provenance)` pairs, never strings. A remediation that
is a string in a rule file is a string that bypasses the emitter, loses provenance, and has
to be maintained per platform by hand.

**DECISION — the preferred remediation form is a declarative graph `patch`, from which the
normal emitter produces the lines.** Literal `lines` are the fallback for what the emitter
cannot yet express.

```yaml
remediation:
  patch:
    - op: set
      target: policy                       # a selector binding, or `self`
      field: perfect_forward_secrecy
      value: { enum: group14 }
```

What this buys:

| | `patch` | `lines` |
|---|---|---|
| Vendor spelling | From the emitter. Correct on every platform the emitter supports. | Written per platform by the rule author, by hand. |
| `Risk` classification | From the emitter's annotation of the emitted line. | Declared by the author, and lint cannot check it. |
| Version-correct syntax | The emitter knows the device's version. | The author has to remember. |
| One-click apply | Yes — it is a graph mutation. Re-lint runs immediately and the user sees the finding clear. | No. Copy-paste only. |
| CI round-trip gate (engine §15.3 gate 2) | Direct. | Requires re-parsing the emitted text. |

**Cost, stated:** `patch` only works for fields the schema models and the emitter emits.
Until emitter coverage is high, most rules will ship `lines`. That is expected and fine —
what is not fine is shipping `lines` for a field the emitter *does* support, so lint warns
when a `lines` remediation's text matches an emittable field.

### 9.2 `patch` operations

| `op` | Fields | Meaning |
|---|---|---|
| `set` | `target`, `field`, `value` | Set a field on a bound node. |
| `unset` | `target`, `field` | Delete a statement. |
| `add_node` | `kind`, `parent`, `fields` | Create a node (e.g. a missing `TrafficSelector`). |
| `add_edge` | `role`, `from`, `to` | Create a relationship (e.g. bind `st0.0` into a zone). |
| `add_to_set` | `target`, `field`, `value` | Add to a set-valued field (e.g. `host_inbound_services`). |

`value` is a typed literal, or a `{ from: "<fex expression>" }` computed from the finding's
bindings. Computed values must type-check against the field's declared type. There is no
free-text value.

### 9.3 `lines` — the fallback, and its template language

**DECISION — remediation templates use `fex` expressions in `{{ }}` holes with a mandatory
explicit renderer. Not Jinja, not Handlebars, not Mustache.**

The rejected alternatives bring loops, conditionals, filters, includes and partials. A
remediation template with a conditional in it is a template with an untested branch, and the
untested branch emits a config line into someone's production firewall. The value of a
template language here is exactly zero features beyond substitution.

```yaml
remediation:
  lines:
    junos-srx:
      - risk: ChangesConfig
        order: 10
        text: "set security ipsec policy {{ policy.name | ident }} perfect-forward-secrecy keys {{ suggested_group | enum }}"
    panos:
      - risk: ChangesConfig
        order: 10
        text: "set network ike crypto-profiles ipsec-crypto-profiles {{ profile.name | ident }} dh-group group14"
```

Hole syntax: `{{ <fex expression> | <renderer> }}`. Exactly one renderer. **No default** —
a hole without a renderer is a build error.

| Renderer | Input type | Output | Rejects (build error at fixture time, evaluation error at runtime) |
|---|---|---|---|
| `ident` | `Str` | Bare identifier | Anything outside `[A-Za-z0-9_.:/-]`; length > 63; leading `-` |
| `quoted` | `Str` | `"…"` with vendor-appropriate escaping | Control characters, embedded newline, embedded `"` that the platform cannot escape |
| `ip` | `Addr` | Canonical (v6 lowercase, RFC 5952 compression) | — |
| `prefix` | `Prefix` | `a.b.c.d/len` | Non-canonical host bits — **error, not silently masked**. A remediation that quietly changes `10.1.2.3/16` to `10.1.0.0/16` has changed the operator's intent. |
| `int` | `Int` | Decimal | Outside the field's schema-declared range |
| `enum` | `Enum` | The platform's spelling from `platform_spellings` (§5.3) | Variant with no spelling for this platform |
| `dur_s` | `Dur` | Seconds as an integer | Non-integer seconds |
| `placeholder` | — | A literal placeholder token, e.g. `"<PSK>"` | **Any real value.** Invariant 3. |

**Why no default renderer.** The failure mode of templating is a value that renders fine in
the fixture and breaks in the field: a VPN named `to-branch (temp)` rendering unquoted, a
prefix with host bits set, a v6 address rendered non-canonically and then compared by
string against the peer's. Forcing the author to name the output alphabet moves all of that
to authoring time.

**Why `placeholder` exists as a renderer at all.** Invariant 3 is that Fathom never accepts
a credential. `placeholder` is the only way a remediation emits the *shape* of a
credential-bearing line, and it is a build error for it to receive a value. Owner brief
§6.2: `set security ike policy IKE-POL pre-shared-key ascii-text "<PSK>"` is emitted; the
engineer pastes the real key into their own terminal.

### 9.4 `risk`, `order`, `rollback`, `verify`

| Field | Meaning |
|---|---|
| `risk` | `ReadOnly` \| `ChangesConfig` \| `Disruptive`. The conventions enum, exactly three values. For `patch` remediations it comes from the emitter and may not be declared. For `lines` it is required. |
| `order` | Integer sort key within a platform. Lines are emitted in `order` then declaration order. Matters: the tunnel interface must exist before a zone can reference it. |
| `rollback` | Same shape as `lines` or `patch`. **Required when any line's risk is `Disruptive`.** Owner brief §6.7: the tool knows what it built, so it can emit the back-out. |
| `verify` | Command corpus ids. Rendered as the "prove it worked" ladder, interpolated with workspace context. The field card's Verify Ladder (side 3) and Bring-Up Order (side 1) are already this structure. |

Continuation style: emitted lines wrap with a trailing `\` at the vendor's own wrap points,
matching the field card (design language, *devices worth stealing*, item 5). The emitter
owns wrapping; templates write one logical line.

## 10. `acceptable_when`

Mandatory on every rule. Invariant 8. Owner brief §5.2: *"This one field is the difference
between a linter engineers trust and one they disable."*

### 10.1 What it must contain

Three things, in this order:

1. **The circumstance.** Concrete, not "in some environments".
2. **The compensating control**, or an explicit statement that there is none.
3. **What to record**, because an accepted exception that nobody wrote down is an accident
   waiting to be rediscovered.

```yaml
acceptable_when: >
  Interoperating with a peer whose platform cannot offer PFS at all — some
  older appliances and a few cloud VPN services. Compensate with a shorter
  Phase 2 lifetime so a compromised IKE SA exposes less recorded traffic,
  and record the peer and the date in the change ticket.
```

### 10.2 When it is never acceptable

Say so, and say why, rather than omitting the field:

```yaml
acceptable_when: >
  Never. A tunnel with no zone bound to st0 cannot pass traffic in any
  configuration — this is not a policy choice, it is an incomplete build.
  If the tunnel is deliberately not carrying traffic yet, deactivate the
  VPN rather than leaving the interface unbound.
```

Lint rejects `acceptable_when: "N/A"`, `"None"`, `"-"` and whitespace, and requires ≥40
characters. The four-word non-answer is the thing this field exists to prevent.

### 10.3 It is not the suppression reason

`acceptable_when` is the rule author's statement of when the finding may be waived. The
suppression's `reason` is the operator's statement of why *this* instance is waived here
(engine §11.2). The UI shows `acceptable_when` next to the reason field when a suppression
is created, so the operator is answering a question rather than filling a box.

## 11. Explainers: the three depths

Owner brief §5.4. Same corpus, three densities, toggled globally and per-block.

| Depth | Audience | Contract | Bounds |
|---|---|---|---|
| `terse` | Knows the platform | The flag, nothing else. Appears as a one-line finding row. | ≤80 chars, one line, no markup, no citation |
| `explained` | Knows networking, new to this vendor | Why this block exists and what to read in the output. Appears in the expanded finding. | 80–400 chars, 1–3 sentences, inline `code` allowed |
| `teaching` | Ramping in | Analogy or background, the failure mode, the counterfactual, and what people misdiagnose it as. Appears in the guidebook and in Teaching depth. | ≥200 chars, no upper bound; use `file:` for anything over ~800 |

### 11.1 Enforceable voice rules

The design language (`.context/design-language.md`, *Voice*) is not decoration. These are
lint gates:

| Gate | Applies to | Rule |
|---|---|---|
| Banned phrases | `why`, `explain.*`, `title` | `simply`, `just`, `powerful`, `seamless`, `robust`, `leverage`, `cutting-edge`, `revolutionise`, `easy`, `merely`. One documented exception: *"Healthy rekey is seamless"* is the card's own phrasing and is allowed inside a quoted excerpt. |
| Failure mode present | `explain.teaching` | Must contain at least one of a small set of failure-mode markers: a "fails/breaks/drops/times out/blackholes" verb, or a quoted vendor error string. |
| Counterfactual present | `explain.teaching` | Must contain "without", "if you do not", "absent", or an equivalent from the locale's marker list. |
| No feature-speak | `why` | Must not begin with "<Thing> provides", "<Thing> allows", "<Thing> enables". The card's rule: *state the failure mode, not the feature.* |
| Citation placement | `explain.terse` | No citations. Terse is a flag, not a footnote. |

**The `why` gate is the important one.** "PFS provides forward secrecy" is a definition.
"Without PFS, one compromised IKE SA secret unlocks every data key derived under it,
including traffic somebody recorded off the wire months ago" is a finding. The lint catches
the first form mechanically and the reviewer catches the rest.

### 11.2 Depth is not truncation

The three depths are three texts, not one text at three lengths. Do not generate `terse`
from `explained` by cutting. Lint warns when `terse` is a strict prefix of `explained`,
because that is the signature of an author who wrote one and truncated it.

## 12. `sources`

### 12.1 Form

```yaml
sources:
  - { std: "RFC 7296", section: "1.3", note: "KE payload for Child SA forward secrecy" }
  - { std: "RFC 8247", section: "2.4", note: "DH group requirements" }
  - { vendor: juniper, doc: "CLI reference: establish-tunnels (Security)", note: "on-traffic is the default" }
  - { card: "srx-ipsec", side: 2, block: "PERFECT FORWARD SECRECY" }
```

| Kind | Fields | Validation |
|---|---|---|
| Standard | `std`, `section`, `note` | `std` matches `^(RFC|BCP|STD|IEEE|NIST SP) [0-9A-Za-z.-]+$`. `section` matches a section-number shape. The linter checks *shape*, not existence — it has no network (invariant 1). |
| Vendor | `vendor`, `doc`, `note` | `vendor` from the platform registry. `doc` is a human-locatable title, not a URL — URLs rot and we cannot fetch them to check. |
| Field card | `card`, `side`, `block` | For content drawn from the owner's own reference cards. Side 1–4, block is the section head as printed. |

### 12.2 The rule about not inventing citations

Conventions: *"If you are not certain a citation is correct, write the claim without the
citation rather than inventing one."*

A rule with no citation is legal, and it must say why:

```yaml
sources: []
sources_note: >
  Observed SRX behaviour with no public document that states it. Verified on
  21.4R3-S5 in a lab; see fixtures/fire-parsed-absent.yaml for the config that
  reproduces it.
```

CI gate 9 requires one or the other. **A fabricated RFC section is worse than no citation**,
because it survives review — nobody looks up a plausible section number — and it is
eventually quoted back to a vendor in a support case.

## 13. References between rules

Four reference fields with four different meanings. They are frequently confused and the
confusion is expensive.

| Field | Affects evaluation? | Meaning | Example |
|---|---|---|---|
| `supersedes` | **Yes** — hides the other finding | "If I fire, the other one is noise." | `ipsec.pfs.absent` supersedes `ipsec.pfs.group-weak` |
| `requires_finding` | **Yes** — gates this one | "I only make sense once the other is true." | A NAT-keepalive rule requires `ike.gateway.nat-detected` |
| `next_if_bad` | No | "This fired; here is what to run or look at next." | `ipsec.traffic-selector.not-mirrored` → `junos-srx/ipsec.inactive-tunnels.show` |
| `related` | No | "Adjacent knowledge." Bidirectional in the UI, declared one way. | `ipsec.pfs.absent` ↔ `ike.dh-group.weak` |

### 13.1 `next_if_bad` chains

Borrowed from the command corpus (owner brief §6.1) and pointed at the same graph. A ref is
one of:

```yaml
next_if_bad:
  - command: junos-srx/ipsec.inactive-tunnels.show     # a command corpus id
  - rule: ipsec.traffic-selector.absent                # another rule
  - explainer: explain:field:IpsecVpn.traffic_selector # a corpus explainer
  - external: true
    label: "Peer vendor's SA log"                      # unresolvable by design
```

The field card's Bring-Up Order (side 1) and Verify Ladder (side 3) are already a directed
graph of "if this, then that". Encoding them here means the verify ladder is generated per
finding rather than printed generically — which is the thing the card cannot do and the tool
can.

CI gate 14: every non-`external` ref resolves within the pack, or is explicitly marked
external. A dangling ladder is worse than no ladder, because the user follows it.

### 13.2 Cross-pack references

Allowed for `supersedes` and `related`, warned for `next_if_bad`, forbidden for
`requires_finding`. Reason: a `requires_finding` edge across packs makes one pack's
behaviour depend on another pack's presence, and a rule that silently stops firing when a
pack is uninstalled is exactly the invisible-failure class this whole design is trying to
avoid.

Unresolvable cross-pack references at load time produce a diagnostic, not a quarantine —
the rule still works, it just cannot link.

## 14. Localisation

### 14.1 What is translated and what is not

| Never translated | Why |
|---|---|
| Rule ids, command corpus ids, explainer ids | They are identifiers. |
| Config lines, command text, field names | An engineer greps for `host-inbound-traffic`. A translated config line is unusable. |
| **Vendor error strings** | `NO_PROPOSAL_CHOSEN`, `TS_UNACCEPTABLE`, `INVALID_KE_PAYLOAD`, `IKE-ID validation failed`. These are the exact bytes in the log the user is staring at. Translating them would make the tool actively harmful. |
| Enum variant names, platform ids | Identifiers. |
| The `Risk` legend text | It matches the printed field card, which is not translated. If a localised card is ever printed, the legend is translated with it, together, and never separately. |

| Always translated | Note |
|---|---|
| `title`, `why`, `symptom_if_mismatched` | |
| `explain.terse` / `explained` / `teaching` | Terse's 80-char bound is a *layout* bound; translations that overflow are a lint warning, not an error — German is longer and truncating meaning is worse than wrapping. |
| `acceptable_when` | |
| `remediation_absent_reason`, `why_chained` | |
| Remediation **comments**, never remediation **lines** | A `#` comment above an emitted block may be localised. The line itself never is. |

### 14.2 Mechanism

Authors write English inline in `rule.yaml` — that is the ergonomic choice and the only one
a non-programmer will tolerate. The build **extracts** it:

```
rules/ipsec.pfs.absent/rule.yaml   ──extract──>   i18n/en.yaml
```

```yaml
# i18n/en.yaml  (generated — do not hand-edit)
rule.ipsec.pfs.absent.title: "Perfect Forward Secrecy is not configured"
rule.ipsec.pfs.absent.why: "Without PFS, Phase 2 keys derive from Phase 1 key material. …"
rule.ipsec.pfs.absent.explain.terse: "PFS not set — Phase 2 keys derive from Phase 1."
rule.ipsec.pfs.absent.acceptable_when: "Interoperating with a peer that cannot support it. …"
```

Key form: `rule.<rule-id>.<field-path>`. Translations are hand-authored files with the same
keys. CI gate 12 fails on any user-visible string that did not extract.

### 14.3 Substitution and fallback

Message strings may contain `{$name}` placeholders bound to the finding's `bindings` and
`witness`, rendered through the same renderer table as §9.3.

```yaml
rule.ipsec.pfs.absent.title: "Perfect Forward Secrecy is not configured on {$policy|ident}"
```

No plural forms in the corpus. Corpus strings talk about one specific node; counts appear
only in UI chrome, which uses the UI shell's own message system (Fluent) where plural rules
belong. Keeping plural machinery out of the corpus keeps the corpus authorable by an
engineer with a text editor.

Fallback chain: **requested locale → `en` → the key itself.** Falling back to the raw key
rather than to blank or to a generic string is deliberate: a missing translation should be
obviously missing, in the UI, to whoever is looking at it.

### 14.4 Translation provenance

A translation file carries the source `rule_version` each string was translated from. When a
rule's English changes, every translation of that key is marked stale and the UI falls back
to English for it, with a small muted marker. A confidently wrong translation of *"PFS on
one side and absent on the other fails Phase 2 while Phase 1 stays up"* is worse than
English.

## 15. Fixtures

Format and CI gates are specified in engine §15. What belongs here is the authoring rule:

**Every rule ships at least one `must_fire` and one `must_pass` fixture, and rules with an
`optional` or `many` binding also ship a phantom-dependency pair** (engine §15.3 gate 5b).

Fixture naming: `fire-<what>.yaml` / `pass-<what>.yaml`. `<what>` describes the *scenario*,
not the outcome — `fire-cbc-no-pfs`, `pass-ikev2-first-child`.

`form: set_config` is strongly preferred over `form: graph`. The card is written in `set`
syntax; fixtures written the same way double as parser tests, and they are reviewable by
someone who has never read the schema.

## 16. `overrides` documents

An organisation adjusting a first-party rule writes an override, not a fork.

```yaml
# acme.internal.overrides/overrides/ipsec.pfs.absent.yaml
overrides: ipsec.pfs.absent
severity: high                 # was: high  — restated for the record
enabled: true
acceptable_when: >
  Never, in ACME's estate. Every peer we terminate supports PFS group14 or
  better. If a vendor claims otherwise, escalate to network security before
  configuring the tunnel.
notes: "ACME NS-0114"
```

**Overridable:** `severity`, `confidence`, `enabled`, `acceptable_when`, `title`, `why`,
`symptom_if_mismatched`, `explain.*`, `tags`, `remediation` **comments**.

**Not overridable:** `condition`, `applies_to`, `requires`, `platforms`, `versions`,
`discriminator`, `supersedes`, `requires_finding`, `remediation` lines or patch.

Engine §12.6 gives the reason: if `ipsec.pfs.absent` means different things in two
workspaces, a rule id in a change ticket means nothing and a fixture suite proves nothing.
Changing logic requires a new rule id in your own namespace, and that new rule may
`supersede` the first-party one.

## 17. Six worked rules

All six are drawn from failure modes stated on the owner's SRX IPsec field card. Explainer
`teaching` text is quoted or paraphrased from the card where the card says it better.

### 17.1 `ipsec.pfs.absent`

Extends owner brief §5.2. Field card side 2, *PERFECT FORWARD SECRECY*.

```yaml
id: ipsec.pfs.absent
rule_version: 2.1.0
status: active
reviewed_by: "<named reviewer>"
reviewed_on: 2026-07-20

severity: high
confidence: definite
category: security
tags: [phase2, crypto, day-one]

platforms: [junos-srx, panos, ios-xe]
versions: "*"
applies_to:
  kind: IpsecPolicy
  with:
    vpn: { via: used_by_vpn, reverse: true, card: optional }
on_unset: pending

condition: "known_absent(perfect_forward_secrecy) || !has(perfect_forward_secrecy)"

title: "Perfect Forward Secrecy is not configured"

why: >
  Without PFS, Phase 2 keys derive from Phase 1 key material. One compromised
  IKE SA secret unlocks every data key derived under it, including traffic
  somebody recorded off the wire months ago.

symptom_if_mismatched: >
  PFS on one side and absent on the other fails Phase 2 while Phase 1 stays up —
  the classic "IKE looks fine but the tunnel keeps dropping". The log shows
  NO_PROPOSAL_CHOSEN on the Phase 2 exchange, not Phase 1.

explain:
  terse: "PFS not set — Phase 2 keys derive from Phase 1."
  explained: >
    `perfect-forward-secrecy keys <group>` on the IPsec policy makes each Phase 2
    negotiation run its own Diffie-Hellman exchange. Without it, every child key
    under this IKE SA falls with the IKE SA. Check the peer sets the same group —
    not merely a compatible one.
  teaching: >
    With PFS, each Phase 2 negotiation runs a fresh Diffie-Hellman exchange, so
    the key is mathematically independent of Phase 1 and of every previous Phase 2
    key. Breaking one yields exactly one rekey interval of traffic and nothing on
    either side of it. That is the "forward" in forward secrecy: today's break
    cannot read yesterday's capture.

    Three things bite. The group must be identical at both ends, not merely
    compatible. PFS on one side and absent on the other fails Phase 2 while Phase 1
    stays up, which is the most misread symptom in IPsec. And the PFS group need
    not equal the Phase 1 dh-group, but matching them removes a whole class of
    confusion.

    Cost is one extra DH exponentiation per SA per rekey — irrelevant unless
    hundreds of tunnels rekey together. Turn it on.

    Under IKEv2 the first child SA is always keyed from the IKE SA regardless;
    PFS applies to later child rekeys. A capture of the initial bring-up showing
    no DH exchange is not a misconfiguration and is not this finding.

acceptable_when: >
  Interoperating with a peer whose platform cannot offer PFS at all — some older
  appliances and a small number of cloud VPN services. Compensate with a shorter
  Phase 2 lifetime so a compromised IKE SA exposes less recorded traffic, and
  record the peer and the date in the change ticket.

remediation:
  patch:
    - op: set
      target: self
      field: perfect_forward_secrecy
      value: { enum: group14 }

verify:
  - junos-srx/ipsec.sa.show
  - junos-srx/ike.sa.detail.show

supersedes: [ipsec.pfs.group-weak]
next_if_bad:
  - rule: ipsec.pfs.group-mismatch
  - command: junos-srx/ipsec.inactive-tunnels.show
related:
  - rule: ike.dh-group.weak

sources:
  - { std: "RFC 7296", section: "1.3", note: "CREATE_CHILD_SA MAY carry a KE payload for stronger forward secrecy of the Child SA" }
  - { std: "RFC 8247", section: "2.4", note: "group14 MUST, group19 SHOULD, groups 2 and 5 SHOULD NOT" }
  - { card: "srx-ipsec", side: 2, block: "PERFECT FORWARD SECRECY" }
```

Two changes from the owner's example, both deliberate:

- `condition` uses `known_absent(...) || !has(...)` rather than `== null`, so that a
  hand-authored node in mid-walkthrough produces a **Pending** entry (via `on_unset:
  pending`) rather than a red finding for a question not yet asked. Engine §2.
- `platforms` uses `ios-xe`, the registry id, rather than `ios`.

The citation change is a proposed correction to the brief; see §20.

### 17.2 `zone.host-inbound.ike-missing`

Field card side 1, plumbing piece #3; side 4, *THINGS THAT BITE*: *"Missing host-inbound
ike. The WAN zone drops the peer's IKE before it is processed. Phase 1 times out with no
local clue. Check this before touching crypto."*

This is the highest-value rule in the pack, because the symptom points nowhere.

```yaml
id: zone.host-inbound.ike-missing
rule_version: 1.3.0
status: active
reviewed_by: "<named reviewer>"
reviewed_on: 2026-07-20

severity: high
confidence: definite
category: correctness
tags: [phase1, plumbing, day-one, most-missed]

platforms: [junos-srx]
versions: "*"

applies_to:
  kind: IkeGateway
  with:
    ext_unit: { via: external_interface, card: one }
    zone:     { via: [external_interface, zone_binding], card: optional }
on_unset: fire

condition: >
  zone == null
  || !zone.host_inbound_system_services.exists(s, enum_is(s, "ike"))

title: "The WAN zone does not admit IKE on the gateway's external interface"

why: >
  The zone that owns the external interface drops the peer's IKE packets before
  the IKE process ever sees them. Phase 1 times out with nothing useful in the
  log, because nothing local ever happened.

symptom_if_mismatched: >
  Phase 1 timeout with no response and no local error. Identical on the wire to
  an upstream ACL, a wrong peer address, or NAT in path — so it is routinely
  misdiagnosed as a crypto problem and people start changing proposals.

explain:
  terse: "WAN zone missing host-inbound-traffic system-services ike."
  explained: >
    `external-interface` is the WAN unit the IKE packets leave by, not `st0`. The
    zone that unit sits in must permit inbound IKE with
    `host-inbound-traffic system-services ike`, or the box drops the peer's IKE
    before processing it.
  teaching: >
    Miss this and Phase 1 times out with nothing useful in the log — the box drops
    the peer's IKE before processing it. That is different from every other
    plumbing mistake: miss the tunnel interface, the zone binding, the route or the
    policy, and the tunnel reads UP while passing zero packets. Miss host-inbound
    ike and nothing comes up at all, and the log has nothing to say about it.

    The error decoder entry for "Phase-1 timeout, no response" lists four causes:
    host-inbound ike, an upstream ACL, a wrong peer address, and NAT. Three of them
    are somebody else's box. This one is yours, it is one line, and it is the
    cheapest of the four to rule out. Check it before you touch crypto.

    Note that this is about the WAN zone, not the VPN zone. `st0.0` also needs a
    zone, for a different reason and with a different symptom — see
    `tunnel.st0.zone-unbound`.

acceptable_when: >
  Never on a gateway that must accept an inbound IKE negotiation. It is acceptable
  only when this gateway is configured `establish-tunnels immediately` towards a
  peer that always responds and never initiates, and the security team has
  deliberately chosen to accept no inbound IKE at all — which is rare, brittle, and
  should be recorded with the peer name and the reason.

remediation:
  patch:
    - op: add_to_set
      target: zone
      field: host_inbound_system_services
      value: { enum: ike }

rollback:
  lines:
    junos-srx:
      - risk: Disruptive
        order: 10
        text: "delete security zones security-zone {{ zone.name | ident }} interfaces {{ ext_unit.name | ident }} host-inbound-traffic system-services ike"

verify:
  - junos-srx/ike.sa.show
  - junos-srx/log.kmd.match-peer

next_if_bad:
  - command: junos-srx/log.kmd.match-peer
  - rule: ike.gateway.external-interface-wrong
related:
  - rule: tunnel.st0.zone-unbound

sources:
  - { card: "srx-ipsec", side: 1, block: "THE FIVE PLUMBING PIECES" }
  - { card: "srx-ipsec", side: 4, block: "THINGS THAT BITE" }
sources_note: >
  Junos behaviour with no single citable document statement; the zone
  host-inbound-traffic model is documented per-statement rather than as this
  consequence. Reproduced in fixtures/fire-no-host-inbound.yaml.
```

`on_unset: fire` is used here because the rule is about a statement's absence on a parsed or
hand-built zone, and a zone with no `host_inbound_system_services` at all is the exact case
we want to catch. It is one of the few justified uses of `fire`.

Note the `rollback` risk is `Disruptive`: removing host-inbound IKE takes the tunnel down at
the next rekey. The rollback for a fix can be more dangerous than the fix.

### 17.3 `tunnel.st0.zone-unbound`

Field card side 1, plumbing piece #2; side 4, *"Tunnel UP, zero traffic. st0 has no zone, no
policy, or nothing routed at it. The SA proves crypto, not reachability."*

The first of the owner's three named cross-node examples.

```yaml
id: tunnel.st0.zone-unbound
rule_version: 1.1.0
status: active
reviewed_by: "<named reviewer>"
reviewed_on: 2026-07-20

severity: high
confidence: definite
category: correctness
tags: [plumbing, day-one, route-based]

platforms: [junos-srx]
versions: "*"

applies_to:
  kind: LogicalUnit
  where: "matches(name, /^st0\\.[0-9]+$/)"
  with:
    zone: { via: zone_binding, card: optional }
    vpn:  { via: bind_interface, reverse: true, card: optional }
on_unset: fire

condition: "zone == null"

title: "Tunnel interface is not bound to a security zone"

why: >
  A logical unit that is in no zone cannot be the source or destination of any
  security policy, so nothing is permitted through it. The SAs come up and the
  interface reads UP, and no packet crosses.

symptom_if_mismatched: >
  Tunnel UP, zero traffic. `show security ipsec security-associations` shows
  Installed, `show interfaces st0.0` shows up, and the byte counters do not move.
  Easily misread as a crypto or selector problem, because the crypto is fine.

explain:
  terse: "st0 unit is in no security zone."
  explained: >
    `set security zones security-zone VPN interfaces st0.0` puts the tunnel
    interface in a zone so a policy can reference it. Without it there is no zone
    pair to write a policy for, and the SRX has nowhere to send the packet.
  teaching: >
    The SA proves crypto, not reachability. Phase 1 and Phase 2 can both be
    perfect while the tunnel passes nothing, and the split between "the crypto
    worked" and "the packet got somewhere" is the most useful diagnostic boundary
    on an SRX.

    Four plumbing pieces produce this same silent symptom: no tunnel interface, no
    zone on it, nothing routed at it, and no policy for the zone pair. All four
    read UP and pass zero packets. Only the missing host-inbound IKE fails loudly,
    and it fails at Phase 1 instead.

    So when the SAs are clean and traffic is not flowing, stop reading proposals.
    Steps 5–8 of the bring-up ladder failing while 2–4 are clean is plumbing, not
    crypto — no proposal tweaking will fix it.

acceptable_when: >
  Never as a finished state. It is acceptable transiently during a staged build
  where the tunnel is being brought up before the zones and policies exist. If the
  tunnel is deliberately not carrying traffic yet, deactivate the VPN rather than
  leaving the interface unbound, so the next person reading the config knows which
  it is.

      role: zone_binding
      from: self
```

### 17.4 `ipsec.traffic-selector.not-mirrored`

Field card side 3, ERROR DECODER: `TS_UNACCEPTABLE — Traffic selectors do not mirror (v2)`.

The second of the owner's three named examples, and the canonical peer-required rule.

```yaml
id: ipsec.traffic-selector.not-mirrored
rule_version: 1.0.0
status: active
reviewed_by: "<named reviewer>"
reviewed_on: 2026-07-20

severity: high
confidence: definite
category: interop
tags: [phase2, selectors, interop]

platforms: [junos-srx]
versions: "*"

applies_to:
  kind: TrafficSelector
  with:
    vpn:     { via: parent_vpn, card: one }
    peer_ts: { via: [parent_vpn, peer_vpn, traffic_selectors], card: many }
requires: [peer_config]
on_unset: skip

condition: "!peer_ts.exists(t, mirrors(self, t))"
discriminator: "name"

title: "Traffic selector does not mirror any selector on the peer"

why: >
  Phase 2 selectors must mirror: this end's local prefix is the far end's remote
  prefix and vice versa. A selector with no mirror on the peer is rejected, and
  the child SA for that pair never installs.

symptom_if_mismatched: >
  TS_UNACCEPTABLE in the log under IKEv2, or INVALID_ID_INFORMATION under IKEv1.
  Phase 1 stays up throughout. On a VPN with several selectors, some child SAs
  install and one does not — so the tunnel looks half-working, and
  `show security ipsec inactive-tunnels` is the command that names which.

explain:
  terse: "No mirroring selector on the peer — Phase 2 will be rejected."
  explained: >
    This selector proposes local `{$local|prefix}` / remote `{$remote|prefix}`.
    The peer must have a selector with those two the other way round. Compare
    against the peer's `traffic-selector` statements, or its proxy-ID under IKEv1.
  teaching: >
    Phase 2 rides inside Phase 1, and it can fail forever while Phase 1 is
    perfectly healthy. That split is the most useful diagnostic fact about IPsec,
    and a selector mismatch is the cleanest example of it: IKE is up, the peer is
    authenticated, and one child SA will not install.

    Under IKEv2 the selectors are negotiated as sets and the responder narrows;
    what it will not do is accept a proposal it has no matching entry for. Under
    IKEv1 the same disagreement appears as a proxy-ID mismatch and reads as
    INVALID_ID_INFORMATION, which is a different string for the same cause.

    `show security ipsec inactive-tunnels` is the underused command here. It names
    what is down and prints a Tunnel Down Reason, which is often the whole answer.
    Read it before you start diffing proposals — the proposals are probably fine.

acceptable_when: >
  Never for a selector that is meant to carry traffic. It is acceptable when the
  peer deliberately runs a wider selector that subsumes this one and its platform
  narrows on acceptance — some cloud VPN endpoints do this. Confirm the child SA
  actually installs before accepting it, and record the peer platform.

remediation_absent_reason: >
  The fix is a decision, not a mutation: either this end's selector is wrong or the
  peer's is, and Fathom cannot tell which is intended. The finding names both
  sides' values so the engineer can choose. Once chosen, editing either end
  produces the emitted lines through the normal path.

verify:
  - junos-srx/ipsec.inactive-tunnels.show
  - junos-srx/ipsec.sa.vpn-name.detail.show
  - junos-srx/log.kmd.match-peer

supersedes: [ipsec.traffic-selector.absent]
next_if_bad:
  - command: junos-srx/ipsec.inactive-tunnels.show
  - rule: ike.version.mismatch
related:
  - rule: ipsec.traffic-selector.default-any

sources:
  - { std: "RFC 7296", section: "2.9", note: "Traffic Selector negotiation and TS_UNACCEPTABLE" }
  - { card: "srx-ipsec", side: 3, block: "ERROR DECODER" }
```

Note `remediation_absent_reason` rather than a remediation. A rule that knows something is
wrong but not which side is wrong must say so. Emitting a line that changes *this* end when
the peer is the one at fault is how a linter breaks a working tunnel.

### 17.5 `ipsec.establish-tunnels.both-passive`

Field card side 4, *THINGS THAT BITE*: *"Both ends on-traffic, or both responder-only.
Nobody initiates, nothing is misconfigured, tunnel never comes up."*

The third of the owner's named examples, and the one that fires on two configs where nobody
wrote a wrong line.

```yaml
id: ipsec.establish-tunnels.both-passive
rule_version: 1.0.0
status: active

reviewed_on: 2026-07-20

tags: [phase2, bring-up, most-missed]

platforms: [junos-srx]
versions: "*"

applies_to:
  kind: IpsecVpn

  canonical: peer
requires: [peer_config]

  (enum_is(establish_tunnels, "on_traffic")

    || enum_is(establish_tunnels, "responder_only_no_rekey"))

    || enum_is(peer.establish_tunnels, "responder_only")
    || enum_is(peer.establish_tunnels, "responder_only_no_rekey"))

       && (has_routed_traffic(self) || has_routed_traffic(peer)))

title: "Neither end will initiate this tunnel"

why: >
  Both ends are configured passively. `on-traffic` negotiates only when a packet
  is routed at st0; `responder-only` never initiates at all. With both ends
  passive and nothing routing traffic in, nobody starts the negotiation.

symptom_if_mismatched: >
  The tunnel never comes up and nothing in the configuration is wrong. No error
  in the log, because no negotiation was attempted. Every proposal, key and
  selector on both sides can be perfect.

explain:
  terse: "Both ends passive — nobody initiates."
  explained: >
    `establish-tunnels on-traffic` is the Junos default, so two ends that never
    set the statement are both passive. `responder-only` is right for a peer
    behind NAT and fatal on both ends at once. Set one end `immediately`.
  teaching: >
    This is the finding that costs the most hours per occurrence, because there is
    nothing to find. Two configurations, both correct, both reviewed, and the
    tunnel does not come up. Nobody wrote a wrong line — `on-traffic` is the
    default, so both ends inherited it.

    `on-traffic` negotiates only when a packet is routed at st0, which means an
    idle backup cycles in the log by design and comes up the first time something
    uses it. That is fine when one end has traffic to send. It is not fine when
    both ends are waiting.

    `immediately` pins the tunnel up from commit. Use it for anything monitored,
    anything carrying a routing adjacency, and anything where failover time
    matters — because a tunnel that comes up on first packet has already dropped
    the first packet. `responder-only` is right for exactly one case, a peer
    behind NAT with no fixed address, and it is fatal on both ends at once.

acceptable_when: >
  Acceptable when a third party genuinely initiates — a dial-in peer, or a
  hub-and-spoke design where the spoke always starts. If neither end is
  `immediately` and the tunnel is expected to be up, this is not acceptable.
  Record which side is expected to initiate and why.

remediation:
  patch:
    - op: set
      target: self
      field: establish_tunnels
      value: { enum: immediately }

rollback:
  patch:
    - op: set
      target: self
      field: establish_tunnels
      value: { enum: on_traffic }

  - junos-srx/ike.sa.show
  - junos-srx/ipsec.sa.show

related:
  - rule: ipsec.vpn-monitor.absent-on-adjacency

  - { card: "srx-ipsec", side: 3, block: "FAKE FLAPS" }
  - { card: "srx-ipsec", side: 4, block: "THINGS THAT BITE" }
```

`canonical: peer` makes this fire once for the pair, not once at each end (engine §4.5). The
finding names both devices.

The third clause of the condition is the honest part: two `on-traffic` ends where either
side actually has traffic routed at `st0` will come up on first packet, so the finding
would be wrong. `has_routed_traffic` is a schema-side derived predicate (a static route or a
routing adjacency pointing at the bind interface).

### 17.6 `mtu.mss-clamp.absent`

Field card side 4, *THE MTU STORY* and *THREE FIXES — KNOW THE DIFFERENCE*.

```yaml
id: mtu.mss-clamp.absent
rule_version: 1.2.0
status: active
reviewed_by: "<named reviewer>"
reviewed_on: 2026-07-20

severity: medium
confidence: probable
category: operability
tags: [mtu, phase2, day-two]

platforms: [junos-srx]
versions: "*"

applies_to:
  kind: Device
  where: "has_ipsec_vpn"
  with:
    flow: { via: flow_settings, card: optional }
on_unset: pending

condition: >
  flow == null
  || (!has(flow.tcp_mss_ipsec_vpn) && !has(flow.tcp_mss_all_tcp))

title: "No TCP MSS clamp for tunnel traffic"

why: >
  IPsec adds roughly 50 to 70 bytes of headers, so a full-size packet entering
  the tunnel must fragment, and firewalls along the path routinely drop
  fragments. Without an MSS clamp the TCP endpoints never learn to send smaller
  segments, because the ICMP that would tell them is filtered somewhere.

symptom_if_mismatched: >
  Ping works. SSH connects. Then `ls` hangs, or a transfer stalls at 0%. Small
  packets fit and full-size ones vanish. Handshake fine, data stalls is MTU until
  proven otherwise — and it is routinely misdiagnosed as a crypto or performance
  problem because the tunnel is up and the counters move.

explain:
  terse: "No tcp-mss clamp — full-size packets will vanish in the tunnel."
  explained: >
    `set security flow tcp-mss ipsec-vpn mss 1360` rewrites the MSS in the TCP
    handshake so both ends agree to smaller segments up front. It is surgical, it
    prevents fragmentation before it starts, and it does not depend on ICMP getting
    through. It is TCP-only and does nothing for UDP.
  teaching: >
    There are three fixes and they are not equivalent. MSS clamping rewrites the
    TCP handshake so both ends agree to smaller segments up front — surgical,
    prevents fragmentation before it starts, needs no ICMP, and does nothing for
    UDP. Lowering the tunnel MTU is universal and covers UDP, but the box now
    fragments before encryption, which costs CPU and produces fragments that can
    still be dropped downstream. Clearing the DF bit lets the network fragment the
    encrypted packet rather than drop it — the rescue when you control neither
    endpoint nor the far side, at the cost of reassembly at the peer.

    Path MTU Discovery is supposed to make all of this unnecessary: the sender sets
    DF, an oversized packet triggers an ICMP fragmentation-needed back, and the
    sender shrinks. It breaks constantly, because that ICMP is filtered somewhere.
    The sender never learns, and big packets disappear in silence. That is exactly
    why MSS clamping exists.

    Rule of thumb: MSS = tunnel MTU minus 40 for the IP and TCP headers. A 1400
    MTU clamps to 1360, and many shops use 1350 for margin. Prefer
    `tcp-mss ipsec-vpn`, which clamps only tunnel traffic, over `tcp-mss all-tcp`,
    which hits everything through the box — a far bigger blast radius than most
    people intend.

acceptable_when: >
  Acceptable when the path MTU is known to be a full 1500 end to end and the
  tunnel MTU has been raised to match, which is realistic only on a private
  circuit you control. Also acceptable when the clamp is applied upstream on a
  router or load balancer rather than on this device — record where.

remediation:
  lines:
    junos-srx:
      - risk: ChangesConfig
        order: 10
        text: "set security flow tcp-mss ipsec-vpn mss {{ suggested_mss | int }}"

rollback:
  lines:
    junos-srx:
      - risk: ChangesConfig
        order: 10
        text: "delete security flow tcp-mss ipsec-vpn"

verify:
  - junos-srx/interfaces.st0.mtu.show
  - junos-srx/ping.df-bit.sized

next_if_bad:
  - rule: mtu.st0.unset
  - rule: mtu.df-bit.copy-with-filtered-icmp
related:
  - rule: mtu.tunnel.too-large

sources:
  - { std: "RFC 1191", note: "Path MTU Discovery; ICMP fragmentation needed is Type 3 Code 4" }
  - { std: "RFC 2923", note: "TCP problems with Path MTU Discovery — the black-hole case" }
  - { card: "srx-ipsec", side: 4, block: "THREE FIXES — KNOW THE DIFFERENCE" }
```

`confidence: probable` rather than `definite`: it is a structural fact that no clamp is
configured, but whether that matters depends on the path MTU, which no configuration
records. The honest label is `probable`, and the rule declares no `requires: [path_mtu]`
because requiring evidence nobody can supply would make it permanently unprovable rather
than usefully approximate. That is the trade, and it is why `confidence` exists as a
separate axis from `severity`.

`suggested_mss` is a schema-side computed value: tunnel MTU minus 40, defaulting to 1360
when the tunnel MTU is unset. The `| int` renderer enforces the field's declared range.

## 20. Proposed change to the owner brief

Conventions require that a contradiction with the owner brief be called out explicitly as a
proposed change with reasoning. There is one.

**Owner brief §5.2 gives `ipsec.pfs.absent` the citation `RFC 7296 §1.3.2`.**

RFC 7296 §1.3.2 is titled *"Rekeying IKE SAs with the CREATE_CHILD_SA Exchange"*. It is
about rekeying the IKE SA itself and requires that a KEi payload be included when doing so.
The statement the rule is actually resting on — that a CREATE_CHILD_SA request may carry a
KE payload for an additional Diffie-Hellman exchange to give stronger forward-secrecy
guarantees for the Child SA — is in **§1.3**, the parent section that introduces the
CREATE_CHILD_SA exchange.

**Proposed:** cite `RFC 7296 §1.3` for the PFS rule, and add `RFC 8247 §2.4` for the group
choice, which is where `group14 MUST`, `group19 SHOULD`, and `groups 2 and 5 SHOULD NOT`
actually come from. §17.1 is written that way.

This is a small correction and it is worth making precisely because of the rule in §12.2:
nobody looks up a plausible section number, and this one would eventually be quoted back to
a vendor.
