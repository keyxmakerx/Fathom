# Attack report — Phase 2 storage design

Five lenses attacked the document (crypto-construction, encryption-tradeoff, shared-credentials, chain-integrity, operational-reality), producing 36 candidate findings. Twenty survived independent adversarial verification; sixteen were refuted and are excluded. After merging findings that several lenses reached from different angles, there are **5 blockers, 7 majors, and 2 items that are minor or unresolved**. Convergence is itself signal: the chain key's custody, the vault audit log, and Mode A's threat model were each found independently by two lenses.

## Blockers — fix before building

**B1. §4 says "wraps" but the binding rule says "derives", so nothing binds a ciphertext to a tenant.** *(crypto-construction, two angles converged)* A wrap involves no derivation, so as written an attacker or a buggy migration can rewrite `tenant_id` on a design blob and its key row and the data decrypts cleanly for the wrong tenant — with every tag verifying. The two readings are mutually exclusive: real derivation would make the custody switch a full re-encryption, contradicting the byte-identical requirement. §7 compounds it: "layer 2 has no such failure mode" is only true if the tenant key comes from the authenticated session, never from the row being read. Nothing says that.
**Fix (corrected):** keep random data keys. Seal `aad_bytes || key` as the wrapped plaintext with the associated-data channel **empty** for key seals; have unwrap return the recovered AAD and compare it at a single path — unequal is `Misbound`, distinct from `Refused`. (WO-12 §4.1 explicitly rejected putting identity in the AAD; do not reintroduce it.) Blob seals keep identity in `info` plus the AEAD. Separately, pin the tenant key from the request context for the request's lifetime. Session pinning alone is what saves cross-tenant separation; the AAD binding buys distinguishable errors and catches design-id substitution within a tenant. Add a test that deletes a tenant filter from a real query and asserts a loud failure. Pick one verb in the diagram, and name the primitive — the approved AEAD is ChaCha20-Poly1305.

**B2. Mode A has no way to share a credential, so Mode B becomes the default for every credential more than one person needs.** *(shared-credentials)* Two engineers needing one enable password have nowhere to go but Mode B. The vault Fathom "cannot read" ends up holding only what nobody uses.
**Fix:** per-credential content key; each user holds an asymmetric keypair generated in-browser, private key stored server-side encrypted under the vault key; the CEK is wrapped once per recipient. The server holds public keys and wrapped CEKs only. Note the cost honestly: §5's stated sharing cost is correct *for the shape it draws* — the shape must change. Revocation is never cryptographic in a client-side scheme; the honest action is rotating the password on the device, and the UI must say so. Design now for the gap where a new hire has no public key yet, and forbid silent fallback to Mode B.

**B3. Mode A claims more than it earns, in two ways.** *(crypto-construction + shared-credentials converged)* (a) Nothing stops the vault passphrase being the login password — which the server receives in cleartext at every sign-in, alongside the stored salt. (b) The same server serves the client; a hostile instance ships JavaScript that captures the passphrase, and Modes A and B collapse on the next page load.
**Fix (corrected):** at passphrase-set time compare against the login password locally in the browser and refuse a match — do **not** ship a verifier to the browser. Better: drop the second passphrase and use a Fathom-generated recovery key. Put Mode A's threat-model sentence in the interface beside Mode B's: protects a stolen database or backup, not a running compromised server. SRI is not a control here (the same server serves the HTML); the real controls are out-of-band signed releases with a published digest, and showing the running client's version and hash. Revise ADR-0042 §3 to say what a *running* compromised instance yields.

**B4. The history chain can be truncated or rolled back and still verify perfectly.** *(crypto-construction + chain-integrity converged)* Each seal binds backwards only. Delete the last three entries and the survivors verify end to end; restore last month's tables and the rollback is cryptographically endorsed. §6 admits whole-design deletion, not this.
**Fix (corrected):** only an anchor outside the database detects it. A periodic tip digest exported from the deployment (owner email, WORM path, or an external witness) is the baseline — the client-remembered-tip variant covers nothing for a design nobody has reopened. A monotonic sequence number in the MAC input is cheap and worth adding, but it does **not** detect tail truncation. Also state who runs verification, how often, and what happens when it fails.

**B5. The chain key is never located, and everywhere it can live in self-hosted Docker is held by the party the log exists to hold accountable.** *(chain-integrity)* It must be live in the server process on every write, so the customer's own admin can recompute every seal.
**Fix:** state custody, scope and rotation in §6 at §4's level of detail, as a key distinct from the master hierarchy, behind the same provider interface, never in PostgreSQL. Then say plainly: this detects a database-only attacker; it does not constrain anyone who can run code on the server. An HSM/KMS makes forgery online and observable, not impossible; only an external witness genuinely constrains the operator. Describe what each buys.

## Majors — fix during Phase 2

**M1. Argon2id is named and nothing else.** *(crypto-construction + shared-credentials converged)* No m/t/p, no salt custody, no nonce rule, no passphrase floor — and the passphrase-derived key encrypts secrets directly, so a passphrase change re-encrypts everything. Fix: passphrase → Argon2id(m,t,p, 16-byte random per-user salt) → KEK; KEK wraps a random vault master key; that wraps per-entry keys; fresh random 96-bit nonce per operation, against ChaCha20-Poly1305. Carry KDF parameters per entry in the schema from day one so they can be raised on next unlock. Compile a refusal floor into the client so a hostile server cannot serve weak parameters. Look the parameters up and cite a source and date — do not quote from memory.

**M2. With per-recipient sharing, the server chooses the public keys.** *(shared-credentials)* It can insert itself as a reader invisibly, and this cannot be retrofitted. Minimum: show fingerprints at share time and pin trust-on-first-use in **local browser state**, with a blocking warning on change. An owner-signed roster is stronger but makes the owner's key a new single point of loss; cost that before choosing. State in §5 which ships in Phase 2.

**M3. The vault's audit log is unsealed, and mode changes are not logged at all.** *(shared-credentials ×2 + chain-integrity converged)* ADR-0042 makes Mode B decryption logging non-optional and the sole compensating control, yet those rows are ordinary table data — weaker than a plain hash chain, while the lower-ranked design history gets a keyed seal. The argument stands on the **database-write** attacker, not the server compromise (already disclaimed). Fix: extend §6's construction to a per-tenant vault audit chain; make mode transitions first-class sealed events including the holder list; move audit sealing out of §8's not-covered list. Also state the rule nobody has written: **who may change a credential's mode**, with re-consent by a current holder on A→B and notification of other holders.

**M4. `content_hash` is undefined, and both readings break something.** *(chain-integrity + operational-reality converged)* Over ciphertext, a key rotation or a payload-format migration invalidates every seal at once — an alarm on every design after a routine `docker compose pull`, indistinguishable from an attack. Over plaintext it is rotation-invariant but a cheap check no longer detects a swapped blob. Fix: define it. If ciphertext, include key id and wrap version and record re-encryption as a first-class chain entry. If plaintext, say routine verification checks links only and content re-binding is on demand. Non-negotiable either way: verification must report three outcomes — verified / broken at entry N / cannot verify under key epoch K — and retired chain keys are kept forever with an epoch id on each entry. §8 cannot defer rotation wholesale; the chain's shape depends on it.

**M5. Re-wrap changes custody, not exposure.** Anyone who held the house master key and a pre-switch snapshot keeps reading data written *after* the customer moves to their own KMS. This is a clarity-and-honesty defect, not a construction one: rotation is not designed out, it is simply never distinguished from re-wrap. Say so in §4, put the re-encryption runbook and its cost in §8, version keys, and make the custody-switch interface say which of the two happened.

**M6. Mode is invisible at the token, the export and the point of use.** A reviewer holding an export cannot tell which credentials the server can decrypt. Display mode beside every `cred_<id>` and give a per-scope count ("14 credentials, 11 server-readable") unconditionally. A mode marker in exports is a **trade**, not free — it tells an export holder what is recoverable from the server — so record it as a deliberate decision.

**M7. Plaintext metadata, and no design name anywhere.** A `pg_dump` discloses the full named org → network → building → rack hierarchy plus authorship and activity volumes, with no key. (This is disclosure of the named topology, not of the drawing — §3's structural-leak argument is about payload internals and still holds.) Two cheap fixes: replace §1's bare "Low" with a one-line threat model that the backup documentation repeats; and settle the design-list question here, as an explicit choice between an encrypted name column decrypted per row and a plaintext one, before implementation settles it silently.

## Minors and open questions

- **Per-version `size` is a device-count and edit-type oracle.** Store a bucketed size, pad ciphertext to the bucket, and name the residual in §3's give-up list. Decide compression explicitly — it is currently unspecified, which is the actual gap. Do not cite ADR-0040 D7 (that rule is about secret material) and do not cite CRIME/BREACH without looking it up. Hardening and disclosure, not a blocker on the schema.
- **UNRESOLVED — whether chain entries need explicit design/tenant binding.** Grafting a genuine run of entries from one design into another succeeds only if the chain key is coarser than per-design, which the document does not say either way. The claim that §4's binding rule pushes identity out of the MAC input was **not established** — §6 says the chain key is not the design key, so §4's rule is not stated to reach it. Resolve by answering B5: if `key_chain` is derived per design from tenant and design identity, grafting fails and no metadata binding is needed — but say so, because today it is inferred. Scoping §4's rule in writing to design-payload keys is cheap insurance against a future misreading.

## What held up

Sixteen findings were refuted, and several load-bearing decisions survived direct attack:

- **Whole-payload encryption over per-field (§3).** The structural-leak reasoning — that encrypting device names while leaving node counts and edge types exposed hands the attacker the estate's shape — was not dislodged. The surviving objections are about the metadata columns beside the payload, not the payload decision.
- **The keyed seal itself.** Against the attacker §6 names — someone who can write the table but does not hold the chain key — the MAC does what it claims: interior entries cannot be rewritten or reordered, because each successor's seal covers its predecessor. Every surviving attack is about what sits *outside* the construction: the tail, the key's custody, and what the hash covers.
- **Byte-identical re-wrap is achievable** and does make a custody switch cheap. The defect is that the document never says what it does *not* do.
- **Tokenisation.** `cred_<id>` in the graph, exports, diagrams and inventory rows leaks nothing on its own; the objection is that it leaks *too little* (mode is invisible), which is a display decision, not a construction flaw.
- **§8's honesty.** The not-covered list genuinely names audit-log sealing and backup/restore. M3 and B4 are arguments about scheduling and severity within an acknowledged gap, not discoveries of a hidden one.
- **Mode B's existing disclaimers.** ADR-0042 §3's "does not protect against full server compromise. This must never be described as though it does," and §5's interface requirement repeating it, held against attack. The gap is that Mode A has no equivalent sentence.
- **§9's own questions did their job.** Question 3 (where does the chain key live) and question 2 (sharing without a server-held key) solicited two of the blockers above. The document asking to be attacked is why they surfaced before the first migration rather than after.

## What to change in the design document

1. **§4** — pick one verb. State the construction in one line: random data keys; key seals wrap `aad_bytes || key` with the associated-data channel empty; unwrap returns the recovered AAD for a constant-time compare; mismatch is `Misbound`, distinct from `Refused`. Blob seals bind through `info` and the AEAD. Name ChaCha20-Poly1305 and the HKDF-from-fresh-salt subkey derivation.
2. **§4** — add: the tenant key is resolved from the authenticated request context and pinned for the request; it is never selected from the row being read.
3. **§7** — replace "layer 2 has no such failure mode" with the conditional truth: layer 2 bites *because of* session pinning, and name the test that proves it (delete a tenant filter from a real query; assert a loud failure, not an empty set).
4. **§4** — add a paragraph: re-wrap changes custody, not exposure. Recovering from a suspected master-key compromise means new design keys and re-encrypted payloads. Version keys so a re-encrypted design is distinguishable from a re-wrapped one.
5. **§5** — redraw Mode A's hierarchy: passphrase → Argon2id(m,t,p, 16-byte random per-user salt) → KEK → random vault master key → per-entry keys. Fresh random nonce per AEAD operation, stated in the text.
6. **§5** — name m/t/p with a cited source and a check date obtained by lookup (CLAUDE.md rule 1). Carry parameters per entry in the schema. Compile a client-side refusal floor. Enforce a passphrase-strength floor at vault creation and say Mode A's strength against a stolen database is bounded by that passphrase.
7. **§5** — add the sharing mechanism: per-credential CEK, per-user keypair, CEK wrapped per recipient, server holds public keys and wrapped CEKs only. State what happens before a recipient has enrolled, and that Mode B is not the fallback.
8. **§5** — add key-directory verification: fingerprints at share time, TOFU pinned in local browser state, blocking warning on change. Say which stronger option (owner-signed roster) ships in Phase 2, if any.
9. **§5** — rewrite line 124. Add Mode A's threat-model sentence to the interface beside Mode B's: protects a stolen database or backup, not a running compromised server. Prevent passphrase reuse by local comparison at set time, or replace the passphrase with a generated recovery key.
10. **§5** — state who may change a credential's mode; require a current holder's re-consent on A→B with the Mode B sentence shown at that moment; notify other holders. Say that revocation means rotating the password on the device.
11. **§5** — display mode beside every `cred_<id>` and add a per-scope count. Record the export marker as a stated trade.
12. **§6** — define `content_hash` explicitly, with the rotation consequences of whichever reading is chosen.
13. **§6** — state `key_chain`'s custody, scope, wrapping and rotation; add an epoch id per entry; retain retired keys. State plainly which adversary the chain excludes and which it does not.
14. **§6** — add a monotonic sequence number (plus design and tenant id) to the MAC input, and an external tip anchor exported from the deployment. Say who verifies, how often, and what happens on failure.
15. **§6** — specify three verification outcomes: verified / broken at entry N / cannot verify under key epoch K.
16. **§6/§5** — extend the chain to a per-tenant vault audit stream; make mode transitions sealed events. Add the tenant-level chain over design creation that §6 already says should exist.
17. **§3** — store a bucketed size, pad ciphertext to the bucket, decide compression explicitly, and name the residual in the give-up list.
18. **§1/§3** — give Structure a one-line threat model (a dump discloses the named topology, authorship and activity volumes) and repeat it in backup documentation. Settle the design-name column as a deliberate choice.
19. **§8** — move audit-log sealing out of the not-covered list; add the re-encryption runbook and its cost beside the existing key-rotation line; stop deferring rotation wholesale, since the chain's shape depends on it.
20. **ADR-0042 §3** — add what a *running* compromised instance yields, alongside the existing stolen-server line.
