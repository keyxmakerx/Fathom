Why results are answer-shaped

A command on its own is half an answer. Every hit carries what to read in the output and what to run next when it is bad. The card's verify ladder is already a directed graph of if this, then that — the corpus just encodes it.

Deterministic, and that is the point

Fuzzy matching and a synonym map. No model at runtime. Works offline, identical every run, diffable between releases.

Emitted config click any line

Emitters return (line, provenance) pairs, never strings. Every line knows the graph node and field that produced it, and every rule that touched it. That is what makes the teaching pillar structural rather than additive.

Credentials never enter the application

The pre-shared key is emitted as a placeholder. There is no reason a config builder needs the real value — the engineer pastes it into their own terminal. This removes the highest-value secret from the threat model entirely.

Miss #3 and Phase 1 times out with nothing useful in the log — the box drops the peer's IKE before processing it. Miss #1, #2, #4 or #5 and the tunnel reads UP while passing zero packets.

Findings continuous lint, not a batch report

Rules are data, not code. One engine; rules carry a platforms and versions predicate. Every rule must state when it is acceptable to ignore it — a linter that flags everything as critical is muted within a week.

Severity is not risk

Finding severity is drawn in neutrals and rule weight. The three colours belong to the risk enum alone — what a command does to a live box. Conflating them would make both meaningless.

Perfect forward secrecy

One corpus, three densities. The senior engineer and the new hire open the same tool. The depth toggle is a margin tab, not a settings panel.

set security ipsec policy IPSEC-POL perfect-forward-secrecy keys group14

Group must match both ends exactly. Absent on one side → Phase 2 fails, Phase 1 stays up.

Without PFS the Phase 2 keys are derived from Phase 1 key material. One compromised IKE SA secret unlocks every data key derived under it — including traffic somebody recorded off the wire months ago.

With PFS, each Phase 2 negotiation runs its own fresh Diffie-Hellman exchange. Breaking one key yields exactly one rekey interval of traffic and nothing either side of it.

set security ipsec policy IPSEC-POL perfect-forward-secrecy keys group14
What breaks, and what you will wrongly blame

PFS on one side and absent on the other fails Phase 2 while Phase 1 stays up. This is the classic "IKE looks fine but the tunnel keeps dropping." You will spend the afternoon re-typing the pre-shared key. The key is fine.

Without PFS the Phase 2 keys are derived from Phase 1 key material. One compromised IKE SA secret unlocks every data key derived under it — including traffic somebody recorded off the wire months ago.

With PFS, each Phase 2 negotiation runs its own fresh Diffie-Hellman exchange. The key is mathematically independent of Phase 1 and of every previous Phase 2 key, so breaking one yields exactly one rekey interval of traffic and nothing either side of it. That is the "forward" in forward secrecy: today's break cannot read yesterday's capture.

The three rules

1The group must be identical both ends, not merely compatible.
2PFS on one side, absent on the other → Phase 2 fails while Phase 1 stays up. The classic "IKE looks fine but the tunnel keeps dropping."
3The PFS group need not equal the P1 dh-group, but matching them removes a whole class of confusion.
set security ipsec policy IPSEC-POL perfect-forward-secrecy keys group14

Cost is one extra DH exponentiation per SA per rekey — irrelevant unless hundreds of tunnels rekey together. Turn it on.

The thing that looks like a bug and is not

Under IKEv2 the first child SA is always keyed from the IKE SA regardless; PFS applies to later child rekeys. A capture of the initial bring-up showing no DH exchange is not a misconfiguration.
