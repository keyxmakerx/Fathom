# README-eos.md — how an Arista EOS config is read

**Status:** Written 2026-11-02 with the `EOS` dialect of `crates/fathom-ingest/src/blockcfg.rs`, on the
owner's sign-off r96 (round 1: "eos reader"). The dictionary is `corpus/dict/eos/config.yaml`; the
platform row `eos` (vendor `arista`) was already in `schema/platforms.yaml`.

## Source

Real EOS configs, generated by Arista's own AVD for its example fabric and published with it:
`github.com/aristanetworks/avd`, `ansible_collections/arista/avd/examples/single-dc-l3ls/intended/configs/`
(`dc1-leaf1a.cfg`, `dc1-leaf2a.cfg`, `dc1-spine1.cfg`), read 2026-11-02. They are what a device is
configured with, not a `show running-config` captured from one, so anything EOS prints that AVD does not
write (a header, `!!` comments, defaults) is not in them.

## The shape

Three-space indentation; a `!` line between top-level blocks; blocks nested in blocks under `router bgp`
(`vlan 11`, `address-family evpn`, `vrf VRF10`) with an indented `!` between their parts; `end` last.
Interface names are one word: `Ethernet1`, `Port-Channel5`, `Loopback0`, `Management1`, `Vlan11`,
`Vxlan1`. Descriptions are not quoted and may hold spaces (`description Make routes learned over MLAG …`).

So the dialect reads indentation where it is there: an indented line never opens a block and an
indented `!` does not end one. A paste that lost its indentation reads by `!` alone, as the TP-Link and
UniFi dialects always do.

## What is read

Hostname; `vlan N` and its `name`; every interface with `description` (the rest of the line), `shutdown`
and `no shutdown`, `ip address`; `channel-group N mode …` as a link of `Port-ChannelN`; `switchport
access vlan`, `switchport trunk allowed vlan` (a list, ranges up to 256 VLANs) and `switchport trunk
native vlan` as VLAN membership; `interface VlanN` as the SVI routing VLAN N, with `ip address` and
`ip address virtual` (the shared anycast gateway); `vrf instance NAME` and an interface's `vrf NAME`;
`ip route PREFIX NEXT-HOP` and `ip route PREFIX Null0`.

## Not read, on purpose

- `ip route vrf …`, and every route a VRF holds: round 2 of r96. Until then the path trace refuses a
  device with a VRF rather than join tables the device keeps apart.
- A trunk with no `allowed vlan` line carries every VLAN, and `allowed vlan 1-4094` says the same: no
  membership is read, so the path trace says it could not establish a way across such a trunk.
- `switchport mode`, `mlag`, `spanning-tree`, VXLAN, BGP, OSPF, route maps, prefix lists: residue.
- `interface Ethernet1` with no `switchport` lines is an access port in VLAN 1 on a real switch; nothing
  in the text says so, so it is not read.

## Credentials

Every line goes through the gate's sweep, and after a credential keyword the rest of the line is
destroyed (the shared rule in `blockcfg.rs`). For EOS: `secret` (`username`, `enable`, `aaa root`),
`password` (BGP neighbours), `key` (`tacacs-server`, `radius-server`, `isis authentication`, a key chain's
`key 1`), `key-string` (added for EOS), `community`, anything ending `-key` (`message-digest-key`,
`authentication-key`, `ntp authentication-key`), and `authentication text` (VRRP). The AVD
`arista.avd.encrypt` filter's documentation names the BGP, OSPF and IS-IS key forms (read 2026-11-02).

**Could not establish:** Arista's own syntax for `snmp-server user … auth … priv …` (no Arista page could
be read, 2026-11-02). The Cisco-style form is assumed, and every word from `auth` or `priv` on is
destroyed; the cost is the algorithm name. Arista's maximum lengths for any credential could not be
established either (`crates/fathom-ingest/tests/arista_eos.rs`, 2026-09-19), so the tests use short ones.

**Could not establish:** whether every EOS release prints a header (`! Command: show running-config`,
`! device: …`) that would make the sniff exact. The sniff is structural instead: an `EthernetN` port
beside a `Port-ChannelN` (capital C) or `ManagementN`, and no `version` line, which IOS and NX-OS both
print.
